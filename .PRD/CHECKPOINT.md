### E-2. 코드 — 감사 잔여 ③ false positive 축소 [그 다음 · 위험 방향] — ✅ 완료 (2026-07-11)
> 근거: 적대적 감사가 재현한 실버그 3건 — `git commit -m "...rm -rf..."` · `echo "rm -rf"` · `grep 'rm -rf'`가 전부 **deny**(언급≠실행 오탐). 4갭은 닫았고 이게 감사의 **마지막 잔여**.
- 🔴 **핵심 위험/충돌**: 유일한 "탐지 약화" 방향. `bash -c "rm -rf ~"`·`eval`·`sh -c`·`python -c`·`node -e`는 **계속 잡아야** 하고, `echo`/`git commit -m`/`grep`의 **인용 인자 안 언급**만 제외. 구별 실패 시 **탐지 구멍**(제품 신뢰 훼손).
- 필수: 감사 배터리(`scratchpad/audit.mjs` 21종)를 회귀로 고정 + `_selftest.mjs`에 FP 잠금 + TDD(11 §5 RED→GREEN→회귀 0).

### 🔴 재평가 — "cp만의 문제"가 아니라 "목적지 피해자 파일" 전체의 문제였음 (실측으로 확정)
- **AE의 표현 정정**: AE는 "cp는 원본이 안 사라지므로 심각도가 훨씬 낮다"고 적었다. 이건 **원본** 기준으로는 맞지만, **목적지에 이미 있던 동명 파일(피해자)** 기준으로는 다르다 — 격리된 임시 폴더에서 4가지 시나리오(mv·cp·Move-Item·Copy-Item, 전부 "목적지 폴더 안에 동명 피해자 파일 존재")를 직접 재현한 결과, **4종 전부에서 피해자 파일이 백업 매니페스트에 전혀 안 잡혔다**(mv/Move-Item은 ask는 뜨지만 원본만 보호·피해자는 무방비, cp/Copy-Item은 확인창조차 없이 완전 통과). `mv`의 (5)번 수정(AC섹션)은 "원본이 사라지는 문제"만 막았을 뿐, "목적지 파일이 사라지는 문제"는 애초에 다루지 않았던 것 — 같은 함수(`writeDestinations()`)가 원인이지만 서로 다른 피해 대상이라 (5)번이 커버 못 한 것.
- **근본 원인(코드 추적)**: `writeDestinations()`가 목적지로 "폴더 자체"만 후보로 잡아 `owExisting` 필터(`existsSync&&isFile()`)에서 걸러진다. 그 폴더 **안**의 실제 덮어쓰기 대상(원본과 동일 파일명)은 후보 목록에 아예 없었다.

2. **1차 구현 후 회귀 테스트로 RED 발견**: `Copy-Item -Path X -Destination Y`(이 순서)에서 피해자가 여전히 안 잡힘. 추적 결과 **더 오래된 사전 결함**을 발견 — 기존 코드가 `-Destination`·`-FilePath`·`-Path`·`-LiteralPath` 4개를 정규식 하나로 뭉뚱그려 문자열에서 먼저 나오는 걸 무조건 "목적지"로 취급하고 있어, `-Path`가 `-Destination`보다 먼저 오면 **원본을 목적지로 오인**하던 버그(이번 신규 기능이 아니라 원래부터 있던 잠복 결함, 이번 TDD 과정에서 처음 표면화됨).
3. **2차 수정**: `-Destination`(목적지)과 `-Path`/`-LiteralPath`(원본)를 완전히 분리된 정규식으로 정확히 구분, 이름있는 플래그로 못 채운 쪽만 남은 위치인자로 보충 — 플래그 순서와 무관하게 항상 정확.
